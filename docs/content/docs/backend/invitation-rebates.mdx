# 邀请返利

所有正常用户均可推广。活动默认关闭，全局比例默认 0，冻结默认关闭；管理员在「邀请返利」统一管理开关、全局比例、冻结期和个人覆盖比例。个人比例为 `null` 表示继承，为 `0` 表示明确不返利。比例使用 0～10000 整数基点，100 基点等于 1%；冻结使用 0～365 个整天，0 表示立即可用。

## 邀请归属

邀请码由用户主动生成，邀请链接形如 `/register?inviteCode=...`。只在创建新账号时绑定一个直接邀请人，长期有效，不补绑、不换绑、不进行多级分佣。注册、验证码消费及邀请写入在同一事务中执行；无效邀请码会使注册回滚，用户可清除邀请码后重试。首个管理员初始化忽略邀请码。

Linux.do 发起时在服务端 OAuth state 保存邀请码；仅创建新用户时绑定，已有身份登录不修改邀请关系。现有协议确认、注册开关和双重验证要求继续生效。匿名校验每 IP 每分钟最多 30 次，只返回有效性，不公开邀请人的身份。用户邀请列表只返回后端脱敏的用户名，不返回邮箱和手机号。

## 订单与返利

返利只来源于被邀请人的在线充值到账积分，包含套餐赠送部分。注册赠送、签到、兑换码、管理员调整、模型消费和返利转入都不触发返利。

下单在商品库存预留事务内保存不可变规则快照，包括是否参与、不参与原因、邀请人、比例、冻结期、计算基数、返利金额和规则版本。同一支付幂等键复用原订单及快照。没有快照的历史订单不补发。

计算为 `floor(到账微积分 × 比例基点 / 10000)`，使用商余分解避免乘法溢出。结果不足一个微积分时不生成返利记录。

支付回调、主动查单及对账补发统一经过 `CompletePaymentOrder`：充值钱包、充值流水、订单状态和返利记录在同一事务提交；返利订单 ID 唯一，失败全部回滚，由支付重试与对账恢复。失败后保留不含数据库原始信息的订单诊断，支付后台显示「处理失败」并提供「重新核验入账」。对账明细也保留「补发失败」，可重新发起核验。第三方已支付不代表站内积分已经到账；数据库完全不可写时诊断也可能暂时无法保存，需依靠通知重试和对账恢复。

可用时间为站内充值积分到账时间加冻结期，不使用客户端时钟或用户访问触发解冻。没有额外的解冻 worker。后台关闭活动、改变比例或暂停推广只影响之后新建的订单，既有快照仍兑现。

## 手动转入

可用返利按 1:1 转为站内积分，可部分或全部转入，无手续费。最小金额为 1 微积分（0.000001 积分），最多六位小数，受现有钱包安全整数上限约束。

转入凭据以用户及请求 ID 唯一。相同请求 ID 和金额重试返回原结果，改变金额复用请求 ID 返回 40901。客户端按账号保存未确认请求，刷新后先查询结果，再使用原 ID 重试；网络超时不能生成新 ID 继续转入。

扣减返利、分摊、增加钱包和积分流水在同一事务执行。按可用时间及记录 ID 分摊，并发时使用所有者写锁及条件扣减。分摊引用独立转入 ID；钱包流水类型为 `promotion_transfer`，引用键为 `promotion-transfer:<transfer ID>`。任一步失败不扣减返利。

累计金额用十进制字符串返回，前端使用 BigInt 计算和展示。概览满足：累计产生 = 冻结中 + 可转入 + 已转入 + 已作废。

## 管理与权限

用户侧入口命名为「邀请有礼」，活动开放时显示在侧栏，账户菜单和 `/promotion` 路由始终保留历史访问。页面按邀请分享、返利账户、邀请与奖励记录组织；累计返利保留历史产生总额，用户只查看可转入、待解锁与已转入积分，不展示后台作废分类和原因。明细显示真实剩余返利，已结束记录不视为全部转入；完整分类和原因仍由管理员账务页面查询。

普通用户只能访问自己的概览、邀请、返利和转入记录。管理员配置使用版本检查，旧版本不能覆盖新配置；个人配置也检查版本。配置加载失败时禁止保存。

启用前先保持活动关闭，配置比例与冻结期，核对充值套餐到账积分（包含赠送）及返利成本，再由管理员主动开启。升级迁移本身不会开启活动，也不会为历史订单补发返利。

管理员可填写原因作废一条记录剩余未转入的返利，不能修改已转入金额。作废与转入竞争时以事务内剩余金额为准。全局规则、个人规则、暂停和作废与审计记录一起提交。

活动关闭后，用户仍可查看历史及转入已有返利。账号禁用沿用现有认证约束。首版不支持现金提现、收款账户、支付退款或自动追扣；外部退款涉及已转入积分时，通过现有管理员积分调整处理，余额不足不得产生负余额。

本次自动化验证已通过：

- 后端 `go test ./...` 和 `go test -race ./internal/promotion`。
- 推广专项同时在 SQLite 与隔离 PostgreSQL 测试库执行，覆盖 v49 升级、旧订单保留、支付幂等与回滚、冻结、并发转入及作废、钱包上限、配置版本与审计回滚。
- 注册服务测试覆盖邮箱、短信、双重验证及模拟 Linux.do；HTTP 测试覆盖权限、数据归属、脱敏、金额字符串和关闭活动后的历史转入。
- 前端 `bun test test/promotion-credits.test.ts`（2 项测试、18 项断言）、`bun run build` 和 `bun run lint`。
- OpenAPI YAML 重复键与本地引用检查、`git diff --check`。

后端专项为 `go test ./internal/promotion ./internal/repository ./internal/auth ./internal/database ./internal/handler ./internal/app`。设置仅用于隔离测试库的 `PROMOTION_TEST_POSTGRES_DSN` 后，推广专项会自动创建独立 schema，执行 PostgreSQL 并发与事务测试，结束后删除该测试 schema。未配置时明确跳过 PostgreSQL 专项。

完整前端测试通过 2360 项。隔离环境的真实页面已核对关闭活动后的历史权益、25 积分部分转入和钱包同步、邀请信息脱敏、普通用户管理页拒绝访问，以及明暗主题和 390px 窄屏排版。CI 必须配置 `PROMOTION_TEST_POSTGRES_DSN`，并验证 PostgreSQL 推广测试实际执行成功，不能静默跳过。

真实邮箱、短信、Linux.do 和支付供应商联调仍需按待测试清单验收；模拟供应商和隔离测试余额不能视为真实支付通过。发布保持活动关闭、比例为 0；生产迁移、备份与发布结果以对应部署验收记录为准。
